# PRODUCT_SPEC_V1.md — FFAX 최종 사용자 경험·모듈 명세

**제품명:** FRONTEND FOUNDRY AX (FFAX)  
**제품 정체성:** AI 기반 프론트엔드 생산·개선·검증 워크벤치  
**목표 시점:** 2026년 12월~2027년 1월 v1.0 검증 목표(일정은 보장 아님)  
**현재 상태:** 아직 제품 코드 없음. 아래는 기능 설계 및 수락 조건의 설명이다.

## 1. 최종 사용 경험

운영자는 대시보드에서 프로젝트를 고르거나 새로 만든다. 기존 GitHub 저장소를 읽기 모드로 연결하면 FFAX가 화면 구조, React 의존성, 라우트, 기존 API/이벤트 사용처를 요약한다. 운영자는 자연어로 "이 서비스를 금융 SaaS처럼 모던한 다크 UI로 바꾸되 로그인·결제·실제 데이터는 건드리지 마"라고 지시한다. FFAX는 **바꾸는 영역/건드리지 않을 영역/라이선스·비용·위험**을 먼저 표시한다.

운영자는 최소 2개 디자인 방향을 비교하고 선택한다. 고정된 디자인 토큰과 UI 컴포넌트 카탈로그를 바탕으로 실제 페이지 코드를 생성한다. 중앙 프리뷰에서 클릭해 본다. 좌측 지시/프로젝트, 우측 속성/컴포넌트/QA 패널로 조정한다. 변경은 하나의 버전/브랜치로 남고 undo/redo 또는 Git revert로 복원된다.

생성이 끝나면 실제 브라우저로 3개 화면 너비, 주요 사용자 행동, 시각 회귀, 콘솔/네트워크, 접근성을 검수한다. 오류가 있으면 생성 작업은 미완료로 유지하고, 수정 후 해당 검사 전체를 재실행한다. 정상인 경우 diff/PR을 보여주며 **운영자의 최종 승인** 이후에만 기존 저장소에 적용한다. Production 배포는 별도 승인 단계다.

## 2. 목표 화면 레이아웃

- **최상단:** 프로젝트/브랜치, 기획→디자인→생성→편집→검증→통합 단계 표시, 현재 작업 상태.
- **왼쪽 사이드바:** 프로젝트·생성 히스토리·디자인 시스템·컴포넌트 카탈로그·비주얼 에디터·QA 리포트.
- **왼쪽 작업 패널:** 자연어 지시, 변경 제한, 첨부 레퍼런스, 모델 선택, 예상 비용, 생성 버튼.
- **가운데 캔버스:** 라이브 웹 화면, 375/768/1440 보기, 확대, 인터랙션 실행, 전후 비교, 선택 요소 강조.
- **오른쪽 패널:** 컴포넌트 삽입, props·토큰·테마 수정, 접근성·반응형 문제, 코드 diff/승인.
- **아래 또는 별도 탭:** 예시 제품 타일(Worknova/KUODRA/RAG/DBVORA), 테스트 리포트, 작업 로그.
- **기본 시각 언어:** 명확한 계층, 간결한 다크 UI, 고대비 텍스트, 적절한 퍼플/블루 하이라이트. 실제 제품마다 테마 분리.
- **레퍼런스:** 콘셉트 포스터는 화면 배치·분위기를 설명하는 **이미지 자료**일 뿐, 실제 작동·성과·배포를 증명하지 않는다.

## 3. 기능 모듈

### M1. Project Intake & Preservation
- 신규 프로젝트, 정적 샘플, 기존 저장소의 안전한 복제/가져오기.
- 파일/브랜치 읽기, 변경 금지 파일·API·기능 목록 관리.
- 기본값은 **read-only 분석**. 코드 변경은 격리 브랜치·검수 PR.
- JSON/SQLite 메타데이터와 소스 저장 영역을 분리한다.

### M2. Requirements-to-Design
- 자연어 → 구조화 브리프: 페이지, 주요 CTA, 입력·출력, 반응형, 브랜드, 접근성.
- 디자인 요구 2안 이상(레이아웃, 색/타이포, 컴포넌트 구성, 트레이드오프).
- 원본 그림은 '참고', 사용자 승인 후 변경.

### M3. Design System
- 브랜드별 테마와 디자인 토큰, dark/light 선택, spacing, typography, borders, shadows, responsive rules.
- 버튼, 카드, 내비게이션, 사이드바, 폼, 테이블, 모달, 알림, 차트 레이아웃·에러 상태.
- 기존 오픈소스는 **라이선스/버전 기록**, 커스텀 확장은 독립 파일로 관리.
- 예시 데이터는 실제 서비스 지표가 아님을 항상 표기.

### M4. AI Generation & Revision
- 모델 공급자 교체 가능한 어댑터(키/프롬프트/출력 스키마, 위험 분석).
- 토큰/비용 제한, 중복 요청 식별자, 생성 일시, 수정 이력, 모델 정보, 실패/재시도 관리.
- AI가 비밀을 요구하면 마스킹 또는 작업 중단; 공급자 전송은 동의 후.
- 생성한 UI가 기존 백엔드 호출을 무단 삭제/변조하지 않는지 diff·테스트.

### M5. Visual Editor
- 컴포넌트 영역 클릭, 계층 선택, 텍스트/색상/타입/간격 변경, 구성요소 재배열.
- undo/redo, 변경 전/후, 충돌 알림, 코드 생성 단위의 상태 동기화.
- 1차 지원 대상을 **등록된 컴포넌트와 구조화 JSON/AST 범위**로 제한. 임의 복잡한 JSX 전체를 WYSIWYG 편집한다고 주장하지 않는다.

### M6. Browser QA
- 실 브라우저(Chromium 등)로 캡처하고 375/768/1440px 스냅샷 저장.
- 레이아웃 깨짐, 가로 스크롤, 텍스트 겹침, 탭·키보드 접근성, 기본 axe 검사, JS 에러와 네트워크 실패 탐지.
- 변경 전 대비 시각 diff와 핵심 클릭 플로 테스트; 실패 시 원인/재현 방법.
- **AI 심미성 평가만으로 PASS 처리 금지**. 도구 검사와 인간 시각 승인 결합.

### M7. Git Integration & Review
- 새 파일/기존 파일 변경 내용과 diff, 변경 금지 파일 탐지, 테스트 리포트.
- GitHub 인증 최소 권한, 독립 브랜치, PR, SHA와 롤백 명령 제공.
- PR merge, main 직접 push, Vercel Production 배포는 별도 사용자 승인.
- 앱이 원본 환경변수·API 토큰을 PR/스크린샷/로그에 쓰지 않게 검사.

### M8. Audit & Operability
- 프로젝트별 생성 작업, 승인 상태, 모델 비용, 예산, 예외, 재시도/작업 취소, 지표.
- 사용자 데이터 보관 기간과 삭제 정책을 별도로 설계.
- 설치/개발/복구/테스트 가이드, 최소 샘플 2종과 재현 가능한 데모.

## 4. 고정된 데모 시나리오(최종 평가용)

**D1 신규 생성:** 로그인·미니 대시보드·리스트/상세·폼 포함하는 React 샘플을 자연어 지시로 제작하고 테마를 바꾼다.

**D2 기존 앱 개선:** API/인증/업무 로직이 있는 테스트용 기존 React 앱을 UI 중심으로 수정한다. 변경 전후 주요 5개 동선을 동일 테스트로 검증한다.

**D3 참고 이미지:** 이용 허가된 콘셉트 이미지 한 장에서 분위기/레이아웃을 추출한 뒤 AI 시안 2개 중 하나를 선택한다. 픽셀 일치/원본 레이어 복원은 평가 대상이 아니다.

**D4 실패 복구:** 모델 호출 실패, API 초과, 생성 중단, 네트워크 끊김, 동일 클릭 반복을 각각 주입하고 재시도/중단/원본 보존을 확인한다.

**D5 검수·반영:** 모바일 overflow 오류를 의도적으로 만들고 QA FAIL → 수정 → PASS → 사람이 PR 내용을 승인 → 격리 브랜치 반영 과정을 재현한다.

## 5. 스펙 밖의 약속 금지
- 한 번의 프롬프트로 항상 상용 최고급 UI를 보장하지 않는다.
- AI 생성 기능이 언제나 코드를 맞게 만든다고 주장하지 않는다.
- 이미지에 적힌 99.8% 등은 시연용 수치이므로 실제 KPI로 쓰지 않는다.
- 소스가 없는 평면 이미지에서 원본 Figma/레이어/모든 세부 스타일을 복원한다고 주장하지 않는다.
- 비용, 배포, 타인 저장소 접근, 인증/보안 변경은 자동 승인하지 않는다.

## 6. 출시물
1. 설치·사용 가능한 FFAX 애플리케이션, 샘플 프로젝트 2개.
2. 재사용 디자인 시스템·컴포넌트 라이브러리·테마.
3. 생성·시각편집·검증·Git 적용 흐름.
4. 릴리스 검증 리포트, 고정 데모, 복구 가이드, 사용·관리 문서.
5. 외부 사용 라이선스 및 원본/레퍼런스 출처 목록.
