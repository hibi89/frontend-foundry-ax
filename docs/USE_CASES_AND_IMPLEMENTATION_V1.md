# FFAX v1.0 — 실용적 사용 시나리오 및 ②·③ 구현 원리

**기준일:** 2026-11-12 KST  
**상태:** 목표 기능/설계 설명, **구현 완료 주장이 아님**. 본 문서는 [REQUIREMENTS.md](../REQUIREMENTS.md), [제품 명세](PRODUCT_SPEC_V1.md), [완성률 AC](ACCEPTANCE_MATRIX.md)를 상세화한다. 기존 AC 12개·가중치·100% 판정 기준 변경 없음.

## A. 왜 만드는가

FFAX는 프론트엔드 개발에서 반복되는 병목인 화면 설계, 디자인 재작업, 기존 서비스와의 통합, QA를 한 작업대(workbench)로 묶는다. 사용자에게 **"프롬프트로 UI 생성 → 눈으로 확인 → 마우스로 수정 → 안전하게 코드 반영"** 경험을 제공하는 것이 핵심이다. 실제 품질은 브라우저/기능 검사 및 사용자 승인으로 확인한다.

## B. ② 자연어 → 새 프론트엔드 자동 제작: 실제 구현 구조

### B1. 사용자 트리거
예: **"글로벌 프리랜서 마켓플레이스, 다크 테마, 검색·프로필·AI 협상 화면을 만들어줘."**

1. 프롬프트/허가된 레퍼런스/브랜드/대상 기기/필수 동선 입력.
2. AI가 **구조화 브리프**를 반환(페이지·컴포넌트·동선·입출력·반응형·테마·금지사항). JSON Schema 검증/누락 확인. 불명확한 기능은 질문/미구현 placeholder 표시.
3. 디자인 플래너가 **서로 다른 2개 시안**을 제안하고 토큰, 레이아웃, 컴포넌트 트리를 산출. 사용자가 시안과 변경 허용 범위를 승인.
4. 컴포넌트 레지스트리에서 버튼·카드·테이블·폼·탐색 등을 가져와 재구성. AI는 자유로운 문자열 코드만 출력하기보다 **엄격한 구조/컴포넌트 계약**을 우선 사용.
5. 안전한 임시 워크스페이스에 React+TypeScript+Tailwind 소스 생성. 데이터가 없으면 명백히 표시된 fixture/mock을 사용하고 실제 API 응답인 듯 표시 금지.
6. 타입 검사·빌드·기본 UI 동선·3개 viewport·콘솔/Network 검증, 실패 로그를 해당 작업 ID에 연결.
7. 브라우저 미리보기 및 수정. 사용자의 확정 후 소스 내보내기 또는 Git 변경사항으로 전환.

```text
Prompt + project context
  -> Scope/security/cost policy
  -> Structured brief + 2 design options
  -> Approved tokens + component tree
  -> React/TS code generation in isolated workspace
  -> Build/typecheck/browser QA
  -> User preview/revise
  -> Versioned export / optional approved Git PR
```

**본질:** LLM은 요구를 구성하고 UI를 제안하는 **설계자**, 컴포넌트 라이브러리는 **검증된 조립 부품**, 코딩·빌드 파이프라인은 **생산 공정**, 브라우저 테스트는 **검수 장치**. AI가 내놓는 결과는 항상 성공하는 것이 아니다.

### B2. AI 산출 예시 (개념 데이터; 실제 구현 포맷은 추후 결정)

```json
{
  "project": "marketplace",
  "pages": ["home", "search", "profile", "negotiation"],
  "design": { "mode": "dark", "accent": "violet", "spacing": "comfortable" },
  "blocks": [
    { "id": "hero-1", "type": "Hero", "props": { "title": "AI × Human" } },
    { "id": "search-1", "type": "SearchBar", "props": { "placeholder": "서비스 검색" } }
  ],
  "restrictions": { "backendChanges": false, "livePayment": false }
}
```

## C. ③ 마우스 → 실제 코드 변경: 작동 원리

### C1. 선택·이동
- **편집 캔버스**: 실행 중인 미리보기와 편집 UI를 분리(iframe/sandbox 및 보안 경계).
- 등록 컴포넌트에는 안정적인 `nodeId`와 구조화된 **컴포넌트 트리/프로퍼티 데이터**를 부여.
- 사용자가 화면의 버튼을 클릭하면 편집 오버레이가 DOM 위치를 계산해 선택 테두리와 속성 패널을 표시.
- 드래그 시 포인터 이동을 부모 컨테이너/그리드의 **정렬·순서·간격 값**으로 해석. 마우스 좌표를 고정 픽셀 CSS로만 박아넣지 않도록 반응형 규칙 적용.
- 변경은 상태 관리의 `SetProp`, `MoveNode`, `InsertNode`, `RemoveNode` 등의 **편집 명령**으로 기록.
- 구조화 데이터 변경 → React 재렌더 → 타입/레이아웃 검증 → 코드 generator 또는 AST-aware patch가 소스에 안전하게 반영.
- 변경 명령의 역연산 또는 상태 히스토리로 undo/redo; 마지막 승인 버전은 Git SHA로 추적.

### C2. 편집된 상태 예시

```json
{
  "nodeId": "cta-register",
  "type": "Button",
  "props": {
    "text": "프로젝트 등록",
    "theme": "primary",
    "alignSelf": "end"
  }
}
```

버튼을 오른쪽으로 옮기면 `alignSelf: "start"` → `"end"` 변경; 색을 바꾸면 `theme` 속성만 변한다. 실제 저장 시 등록된 `Button` 컴포넌트의 props와 허용된 container layout에 맞추어 React 코드 패치한다. 즉 **보이는 화면과 코드가 둘 다 같은 구조 데이터를 바라보게 하는 것**이 원리다.

```text
Pointer click/drag
  -> identify nodeId + parent layout
  -> edit structured property or component tree
  -> render updated preview immediately
  -> save reversible command/event
  -> generate minimal React/TS patch
  -> QA + human review -> Git branch/PR
```

### C3. 기술 선택지와 범위

| 안 | 구조 | 속도·비용 | 유지보수·제약 | 권고 |
|---|---|---|---|---|
| A | 모든 JSX 소스에 대한 일반-purpose AST 시각 편집 | 초기 통합 비용 높고 예외가 많음 | 복잡한 조건부 렌더·커스텀 훅·동적 상태에서 코드/화면 매핑이 어려움 | v1 비권장 |
| B | **등록된 컴포넌트 + typed JSON/AST + 명령형 편집** | 초기 레지스트리 비용이 있지만 예측 가능 | 편집 가능 범위를 명시할 수 있고 테스트·diff·undo 쉬움 | **v1 권고** |

기술 후보: React/TypeScript, 등록 컴포넌트, 안전한 iframe preview, pointer/drag-n-drop 라이브러리(예: dnd-kit), 선택적 시각 편집기 엔진(예: Puck), 명령형 undo/redo, AST 기반 제한적 코드 변환. 채택 전 라이선스·번들 크기·보안·유지보수 확인 필요.

**한계:** 임의의 웹사이트, 임의의 동적 JSX, 비공개 디자인 파일 전체를 완벽한 WYSIWYG로 편집할 수 있다고 약속하지 않는다. 이미지로부터 원본 레이어 복구도 불가능하거나 부정확할 수 있다. 외부 코드를 실행할 경우 격리·권한·스크립트 검사 필수.

## D. 운영 흐름과 구매자 요구 수용

고객의 자연어/텍스트 요청 → 변경 범위 식별 → 변경 금지 경계(비밀·백엔드 API·회원·결제 등) 확인 → 시안 2개 → 고객/운영자 승인 → 안전한 UI 패치 → 기존 기능 회귀 테스트 → PR/납품.

고객 요구를 받는 **입력 양식·변경 요청 이력**은 유용하지만, 고객용 멀티 사용자 협업/외부 승인 포털은 v1 필수 범위를 초과할 수 있다. 외부 사용자·고객 데이터 전송은 별도 승인/보안 설계를 우선한다.

## E. 수익화 가능 모델 (검증 전 가정)

1. **내부 생산 도구:** 여러 자체 제품의 UI 개발·개선 시간을 절감, 고객 요구 대응 표준화.
2. **설치형 개발/디자인 도구:** 라이선스를 준수하는 범위에서 프로젝트 생성·시각 편집·QA를 제공하는 패키지 판매.
3. **구독형 SaaS:** 모델 호출, 저장 공간, 작업량, 협업, 인증/결제, 법적 고지까지 운영 체계 확보 후 확장.

**권고 순서:** 내부 프로젝트 3개 이상에서 실제로 품질/시간/오류율을 측정 → 설치형/납품형 상품화 검토 → 충분한 수요와 운영 여력이 확인되면 SaaS 전환.

## F. 생산성 가설과 측정 (예측값을 성과로 표시하지 않음)

예전에 설명한 **"기존 20시간 ↔ FFAX 6시간 (70% 단축)"은 효과를 설명한 가상의 목표 시나리오**이며 어떤 실측 데이터도 없다. 예를 들어 "일반 관리자 대시보드 UI"의 고정 작업을 동일한 개발자·하드웨어·요구·기능·검수 기준으로 3회 이상 반복하고 다음을 기록해야 효율 향상 주장이 가능하다.

- **T0** 요구 확정 → 디자인 시안 확정 → 첫 정상 빌드 → 사용자 최종 수락까지의 경과 시간.
- **재작업 지표:** 디자인 수정 요청 횟수, 수작업 코드 변경 횟수, 모바일/기능 회귀 결함 수.
- **품질 지표:** 접근성/반응형/핵심 사용자 동선 통과율, 최소 3개 화면 너비.
- **비용 지표:** LLM 입력/출력 토큰, 실제 API 청구/추정, 개발·테스트 시간.
- **공정성:** 기존 AI 개발 방식 vs FFAX, 동일 요구·검증·기존 원본. 동일 화면 스냅샷만 비교하고 기능 검증을 생략하는 방식 금지.
- **결과:** 각 시나리오의 분포(평균·중앙값), 실패·추정·측정값을 구분해 보고.

목표는 *"70% 절감"*을 선언하는 것이 아니라 **네가 실제로 지시하고 검수하는 시간이 줄었는지** 증명하는 것.

## G. 완료 기준으로 연결

- **새 화면 생성:** AC-02 + AC-03 + AC-04와 D1 데모.
- **마우스 편집:** AC-06, 코드·미리보기 동기화와 undo/redo 자동 테스트.
- **기존 제품 개선:** AC-07 + AC-08 및 복구점.
- **이미지 참조:** AC-05와 라이선스/권리 증거.
- **상용 준비:** 추가적인 법률/운영 정책과 독립적 수익성 검증. 해당 수익성은 FFAX v1 100점에 자동 포함되지 않는다.
- 출시 완성률 정의는 기존 AC 기준을 유지하며, 모든 Release Gate를 별도 통과해야 한다.
